# Contributing

Thanks for contributing.

Repository-specific contribution instructions take precedence over this shared default. Before making a change, check the target repository for its own `CONTRIBUTING.md`, README, development documentation, issue templates, and test instructions.

## Before opening an issue

Search existing issues first. When reporting a bug, include enough information for someone else to understand and reproduce it. When proposing an improvement, explain the problem or opportunity as well as the desired outcome.

Do not include passwords, API keys, private logs, personal data, or other sensitive information in issues or attachments.

Security vulnerabilities should not be reported through a normal public issue. Follow the repository's `SECURITY.md` instead.

## Before opening a pull request

Keep changes focused on one coherent purpose. Follow the target repository's formatting, linting, testing, and documentation conventions.

For substantial or potentially breaking changes, check whether the repository asks contributors to discuss the proposal in an issue or discussion before implementation.

A useful pull request should explain:

- what changed;
- why the change is needed;
- the related issue or context, when applicable; and
- how the change was verified.

Add or update tests and documentation when they are relevant to the change. If a normal verification step cannot be run, say so clearly in the pull request rather than leaving the reviewer to infer it.

## Reviews

Review feedback is part of the contribution process. Address substantive comments, resolve misunderstandings with evidence, and keep discussion focused on the work.

Maintainers may ask for a change to be split, reduced in scope, or adapted to repository-specific constraints before it can be merged.
